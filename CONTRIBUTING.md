
# Contributing to PocketMC

PocketMC is an independent hobby project developed by CesarDev / ByCesarDev at the maintainer's own pace. The project is maintained primarily for the maintainer's own goals and interests.

Bug reports, suggestions, and pull requests are welcome, but there is no guarantee of a response, fix, review, or merge. All accepted changes are reviewed by the maintainer before being included in the project.

Please write in English and keep your messages concise. Clear, focused reports are easier to review. Machine translation is welcome if English is not your first language; you may include the original text below the translation.

Be respectful. The maintainer may close issues or pull requests that are irrelevant, duplicated, unclear, out of scope, or inconsistent with the project's direction.

## Issues

Before opening an issue, check whether the problem or request has already been reported.

Please use a descriptive title and keep each issue focused on one topic.

- **Bug reports:** Describe what happened, what you expected to happen, and the steps required to reproduce the problem. Include your operating system, build or commit, relevant logs, and any other details needed to reproduce the issue.
- **Feature requests:** Explain what you want to add and why. Mention any relevant technical limitations or possible approaches if you know them.
- **Build problems:** Include the build configuration, compiler and toolchain versions, the command you ran, and the complete relevant error output.
- **Questions or other topics:** Provide enough context for the maintainer to understand what you need.

Do not include passwords, access tokens, private keys, or other sensitive information in issues or logs. Check logs for personal information before posting them publicly.

PocketMC aims to reconstruct the behavior of Minecraft Pocket Edition 0.6.1. Reports involving unrelated versions, platforms, or behavior outside the project's scope may not be addressed.

Feature requests may be accepted, postponed, or declined depending on the project's goals, technical feasibility, and the maintainer's available time. Opening an issue does not guarantee that a feature will be implemented.

## Security

Please do not publish exploitable security vulnerabilities, private information, or sensitive security details in public issues.

Report security concerns privately through GitHub's available security reporting features, if enabled for this repository. If private reporting is unavailable, contact the maintainer through an appropriate private channel before disclosing the details publicly.

## Pull requests

Pull requests are welcome, but please discuss substantial changes in an issue before investing significant time in implementation.

| Change                             | Guidelines                                                                                     |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- |
| Documentation fixes                | Welcome; a prior discussion is usually unnecessary.                                            |
| Small bug fixes                    | Welcome, provided the fix is focused and can be verified.                                      |
| Larger features                    | Please open an issue first. The maintainer may request changes or decline the contribution.    |
| Build system or dependency changes | Discuss these beforehand, as they can affect compatibility, reproducibility, and distribution. |
| Large refactors                    | Discuss the proposed design before submitting a pull request.                                  |

Keep each pull request focused on a single logical change. Explain what changed, why it is needed, and how it was tested.

Do not assume that a pull request will be merged simply because it builds successfully or passes automated checks.

The maintainer may modify, reorganize, request changes to, or decline any contribution to preserve the project's architecture, compatibility, and overall direction.

## Code and project conventions

Follow the conventions already established in the relevant part of the codebase.

- Prefer clear, maintainable code over unnecessary complexity.
- Keep changes focused and avoid unrelated formatting or refactoring.
- Preserve existing behavior unless the change explicitly intends to modify it.
- Avoid introducing dependencies without a clear technical reason.
- Document non-obvious behavior and important technical decisions.
- Do not claim that a feature has been tested if it has not been tested.

If the repository contains specific build instructions, architecture documentation, or coding conventions, follow those instructions when making changes.

## AI-assisted contributions

AI-assisted code and documentation are allowed.

Contributors remain responsible for the correctness, originality, licensing, security, and maintainability of the changes they submit. Review generated code before submitting it and verify that it does not introduce copied code, incompatible dependencies, or unlicensed third-party material.

- You wrote the contribution yourself, or you have identified its source.

- Your contribution does not violate another project's license or any applicable third-party rights.

Do not submit copied proprietary code or third-party materials without the necessary permissions.

The project maintainer may request clarification about the origin or licensing of a contribution and may decline contributions whose provenance or licensing cannot be established.
